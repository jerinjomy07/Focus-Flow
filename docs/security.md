# FocusFlow — Security Architecture

This document describes the security controls implemented in Phase 11 and the rationale behind them. Production deployment hardening (WAF, TLS enforcement, Redis rate limiting, managed secrets) is deferred to Phase 12.

---

## 1. Route Protection

All authenticated workspace routes are protected by `src/middleware.ts` via Auth.js v5.

### Protected Route Matrix

| Route | Protection |
|---|---|
| `/dashboard/*` | ✅ Auth required → redirect to `/login` |
| `/focus/*` | ✅ Auth required → redirect to `/login` |
| `/tasks/*` | ✅ Auth required → redirect to `/login` |
| `/projects/*` | ✅ Auth required → redirect to `/login` |

Authenticated users who have not completed onboarding (`User.onboardedAt = null`) are redirected to `/onboarding` when accessing any workspace route.

## 2. Security Headers

All HTTP responses include these headers (configured in `next.config.ts`):

| Header | Value | Purpose |
|---|---|---|
| `Strict-Transport-Security` | `max-age=63072000; includeSubDomains` | Enforces HTTPS on all subsequent requests (Production only) |
| `X-Content-Type-Options` | `nosniff` | Prevents MIME-type sniffing attacks |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | Limits referrer information leakage |
| `X-Frame-Options` | `DENY` | Prevents clickjacking via iframes |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=()` | Denies unused powerful browser APIs |
| `Content-Security-Policy` | See below | Restricts resource loading origins |

> [!NOTE]
> `Strict-Transport-Security` (HSTS) is active strictly when `NODE_ENV === 'production'` to prevent TLS transport errors during local HTTP development.

### CSP Policy

```
default-src 'self';
script-src 'self' 'unsafe-inline';
style-src 'self' 'unsafe-inline';
img-src 'self' data: blob:;
font-src 'self' data:;
connect-src 'self';
media-src 'none';
object-src 'none';
frame-src 'none';
frame-ancestors 'none';
```

`'unsafe-inline'` is required because Next.js injects inline scripts for hydration and Tailwind uses inline styles. A nonce-based CSP can be implemented in Phase 12 when server-side nonce injection is configured.

## 3. CSRF / Origin Validation

`src/middleware.ts` validates the `Origin` header on all `POST`, `PATCH`, `PUT`, `DELETE` requests to `/api/*` paths (excluding `/api/auth/*` which handles its own CSRF tokens internally).

**Logic:**
- If the `Origin` header is absent: request proceeds (same-origin requests and server-to-server calls may omit it).
- If the `Origin` header is present and its host matches the server's `Host`/`x-forwarded-host`: request proceeds.
- If the `Origin` header is present and its host **does not** match: request is rejected with `403 Forbidden`.

This protects against cross-site request forgery attacks from malicious third-party websites.

## 4. Rate Limiting

FocusFlow implements application-level rate limiting in `src/lib/rate-limit.ts` using a sliding-window token bucket.

### Implementation

- **Dual Mode (Serverless & Distributed)**:
  - **Production with Upstash / Vercel KV**: When `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` are provided, rate limits are enforced via HTTP REST pipeline requests (`INCR` + `EXPIRE`). This ensures consistent rate-limit enforcement across distributed serverless instances.
  - **Fail-Open Fallback & Local Development**: If Redis credentials are absent or if an Upstash network/timeout error occurs, the rate limiter safely fails open to an in-memory sliding-window bucket, preventing authentication outages during third-party dependency degradation.
- **Algorithm**: Sliding window per key.
- **Interface**: `RateLimiter { check(key: string): Promise<RateLimitResult> | RateLimitResult }`. All callers in middleware and route handlers invoke `await limiter.check(key)`.

### Applied Limits

| Endpoint | Limiter | Limit | Key | Interception Point |
|---|---|---|---|---|
| `POST /api/auth/register` | `authLimiter` | 10 req / 60s | Client IP | Route Handler (`src/app/api/auth/register/route.ts`) |
| `POST /api/auth/callback/credentials` | `authLimiter` | 10 req / 60s | Client IP | Middleware (`src/middleware.ts`) |
| `POST /api/focus-sessions` | `apiLimiter` | 60 req / 60s | User ID | Route Handler (`src/app/api/focus-sessions/route.ts`) |

#### Login Rate Limiting Decision
NextAuth (Auth.js v5) executes credential logins via `POST /api/auth/callback/credentials`. The route handler is generated by NextAuth's `handlers.POST` export, making route-level wrapping impractical without modifying framework internals. Therefore, rate limiting for login attempts is enforced in `src/middleware.ts` before the request reaches the Auth.js handler. Both registration and login share the same strict threshold (10 requests per 60 seconds per client IP) to protect against credential stuffing and brute-force attacks.

## 5. Mass-Assignment Protection

All Zod schemas that process `POST`/`CREATE` request bodies use `.strict()` to reject unknown fields. This prevents clients from injecting unexpected properties.

Schemas with `.strict()`:
- `RegisterSchema`
- `CreateProjectSchema`
- `CreateTaskSchema`
- `StartSessionSchema`
- `UpdateProjectSchema`
- `UpdateTaskSchema`
- `UpdateSettingsSchema`
- `UpdateNotificationPreferenceSchema`
- `UpdateGoalSchema`
- `UpdateUserSchema`

---

## 6. Structured Error Logging

Unknown/unexpected 500 errors are logged via `pino` (see `src/lib/logger.ts`) before returning a generic `INTERNAL_ERROR` response. This ensures:
- Internal error details are **never** sent to clients.
- Errors are captured in structured JSON logs for production observability.

Sensitive fields are automatically redacted from all log output: `password`, `passwordHash`, `token`, `authorization`, `cookie`, `secret`, `apiKey`.

---

## 7. Multi-Tenant Isolation

All database queries are scoped to the authenticated user's `userId`. Cross-user access returns `404 NOT_FOUND` (anti-enumeration — never `403`).

## 8. Dependency Security Audit Status

Dependency vulnerabilities were systematically audited in Phase 11 using `npm audit`.

### Audit Summary

| Metric | Value |
|---|---|
| Command | `npm audit` |
| Total Dependencies Evaluated | 746 (165 production runtime, 509 development) |
| Production Runtime Vulnerabilities | **0** |
| Development Tooling Vulnerabilities | 2 moderate (development-only) |

### Reported Development Vulnerabilities

- **Package**: `@vitest/mocker` (`3.2.7`) via `vitest` (`3.2.7`)
- **Severity**: Moderate (CVSS 5.9, CWE-22 Path Traversal, [GHSA-82fw-gwwq-j7x9](https://github.com/advisories/GHSA-82fw-gwwq-j7x9))
- **Scope**: **Development Only (`devDependencies`)**
- **Production Impact**: **Zero**. Vitest and `@vitest/mocker` are test runner libraries executed only during local development and CI testing (`npm test`). They are never included, imported, or packaged in the production Turbopack build (`.next/standalone` / runtime output).
- **Remediation Analysis**:
  - The patch was introduced in Vitest `4.1.11` / `5.0.1`. No patch exists for the 3.x branch.
  - Upgrading to Vitest 4 or 5 is a breaking major-version change that creates peer-dependency resolution conflicts (`ERESOLVE`) with `@vitejs/plugin-react` and `vite@^8.3.0`.
  - Running `npm audit fix --force` would force-downgrade or alter peer dependencies, destabilizing the tested test suite.
  - **Resolution**: Kept at `vitest@3.2.7` for Phase 11 stability. Scheduled for synchronized toolchain upgrade in Phase 12.

## 9. Phase 12 Security Implementations & Post-Launch Considerations

### Implemented in Phase 12
- **TLS Enforcement & HSTS**: Added `Strict-Transport-Security` header (`max-age=63072000; includeSubDomains`) in production via `next.config.ts`.
- **Distributed Rate Limiting**: Deployed REST-based Upstash Redis / Vercel KV rate limiting with atomic pipeline commands and fail-open in-memory fallback.
- **Serverless Secret Management**: Configured production secret separation via Vercel Environment Variables (`DATABASE_URL`, `DIRECT_URL`, `AUTH_SECRET`, `UPSTASH_REDIS_REST_TOKEN`).
- **Liveness & DB Health Probe**: Implemented `GET /api/health` protecting against internal error leakage while reporting DB connection status.
- **Vercel Build Security**: Standardized build command `prisma generate && next build` in `vercel.json` without exposing environment variables or build artifacts.

### Post-Launch Backlog
- **WAF Rules**: Fine-tune custom Vercel Firewall rules based on live traffic access logs.
- **Nonce-based CSP**: Migrate from `'unsafe-inline'` to dynamic cryptographic nonce injection in Next.js middleware once full SSR streaming audit is performed.
- **Security.txt**: Publish `/.well-known/security.txt` for coordinated vulnerability disclosure.
- **Dev Toolchain Major Version Alignment**: Synchronously upgrade Vite 8, `@vitejs/plugin-react`, and Vitest 4/5 when upstream peer dependencies publish stable compatibility.
